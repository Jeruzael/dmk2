# DMK2 Phase 1 Implementation Plan

> Execute inline using superpowers:executing-plans. The user supplied the complete implementation authorization and publication scope; no further design approval is needed.

**Goal:** Deliver the smallest reliable Agent → stdio MCP → SQLite → Electron → history → portable package workflow.

**Architecture:** Shared synchronous local service with validated domain schemas, WAL, transactional events and optimistic concurrency. Electron main and independent MCP processes each open the same SQLite file. Sandboxed React renderer uses a narrow preload bridge.

**Tech stack:** Electron, React, strict TypeScript, Vite, built-in node:sqlite, official MCP TypeScript SDK, Zod, react-markdown, remark-gfm, Node test runner and Playwright Electron smoke tests.

**Spec:** User's Phase 1 implementation brief supplied 2026-11-04 (acceptance obligations summarized below).

## Global constraints

- Local only; no accounts, provider requests, TCP backend, credential broker or DMK1 source/data.
- Every successful domain mutation includes an event in the same transaction.
- Operation IDs bind to canonical request contents; updates require current revisions.
- No arbitrary shell/filesystem MCP tools; package contents are structured records only.
- Preserve source labels separately from execution status; user approval is a recorded claim.
- Keep runtime data outside Git. Publish a feature branch and Draft PR; never merge.

## Review focus

- Competing writers and startup migrations must serialize without corrupting or dropping data.
- Reused operation IDs with different contents must fail; retries must return the original result.
- Malformed packages (including forged histories and cross-project links) leave no partial state.
- Markdown/URLs must not execute scripts, load remote resources or navigate the app.
- Package round trips preserve every revision/event and remain usable after restart.
